# Silid — agent instructions (repo root)

**Read first:** `spec/00-master-goal.md` and the header JSON at the top of
`PROGRESS.md`. The spec is the source of truth. This file is the short
operational form of the rules that bind every session and every agent instance
working in this repo. Where the two disagree, the spec wins and this file is
wrong — fix it in the same commit as whatever exposed the disagreement.

This file is enforced, not advisory: `rule-lint` fails the build if the
Supabase mandate below goes missing.

---

## 1. Supabase: the MCP server and the official skill are mandatory

For **every** Supabase task, in **every** session and **every** agent instance.
No exceptions, and "the CLI was quicker" is not one.

- **Use the Supabase MCP server.** Schema iteration, SQL execution, applying
  reviewed migrations, running policy tests, inspecting advisors, reading logs,
  and looking up live documentation all go through it. Discover its tool
  surface at time of use — from the server's own tool list, or `--help` for the
  CLI — and never recall tool names or arguments from memory.
- **Load the official Supabase agent skill** for any Supabase task
  (`npx skills add supabase/agent-skills`, then the `supabase` skill). Schema,
  function, RLS, and migration work is verified against the skill and the live
  docs, not reconstructed from training data. The companion
  `supabase-postgres-best-practices` skill is loaded before writing or changing
  anything that lives in Postgres.
- **Wiring is whatever the harness supports** (`spec/supabase.md` §3): a
  repo-root `.mcp.json` for harnesses with project-scoped MCP config, the
  harness's documented pattern otherwise, never an invented path. That file is
  local-only and gitignored, so its absence from the tree is correct, not a
  defect. The project ref is recorded in `spec/deployment-operations.md` §2 —
  read it from there, never from memory.
- **Forbidden bypasses.** No direct Postgres connection: no `psql`, no
  `postgres://` or `postgresql://` connection string carrying credentials, no
  database password in an env var, no `service_role` key in any client. When
  the MCP server genuinely cannot do something, that is a gap to report and park
  in `DECISIONS-NEEDED.md` — it is never a licence to connect directly.

RLS remains the backstop and is never a setting to be relaxed: tenancy
identifiers stay client-derived, and no write trusts a client-supplied actor or
timestamp. The server never stores an authoritative timestamp that came from a
client, and never accepts one for audit.

## 2. Generate, don't hand-write

Anything a tool can generate is generated by the tool, and the exact command is
recorded with the work: `shadcn` for components, `pnpm` for installs,
`playwright init` for E2E scaffolding, the `supabase` CLI/MCP for schema,
migrations, and policy tests. Hand-writing a generatable file is a defect. Where
no generator exists, the rationale is recorded next to the file.

**Reuse what the repo already ships before building it again.** Two that have
been missed before, both load-bearing:

- pgTAP suites in `supabase/tests/*.sql` run through the existing capture
  wrapper: `node packages/testing/src/wrap-pgtap-capture.mjs`, then the wrapped
  suites in `.tmp-pgtap-wrapped/`. It exists because the Management API query
  path returns only the last result set, so the TAP lines have to be captured
  into a table to be readable at all. Re-deriving that table by hand is a
  reinvented wheel, and it has already happened once.
- Coverage and mutation gates run through the package's own
  `@silid/testing` config and Stryker setup, not a hand-rolled runner.

## 3. Verify before you trust

Every claim is checked against the thing itself, at the moment of use: files on
disk, `--help` output, the package registry, live documentation, the live
database. Real command output is pasted, not paraphrased. `UNVERIFIED` is an
acceptable answer; a confident guess is not. When the prompt, the spec, and the
disk disagree, the disk wins and the discrepancy is logged rather than
silently reconciled.

## 4. The ledger

Two ledgers, never mixed and never conflated: **guest billing** and **platform
billing**. Every peso figure that lands in a report, gate, or ledger trace is
recomputed from source rows by the Money Recomputation Gate rather than carried
forward from a previous total.

## 5. PROGRESS.md discipline

`PROGRESS.md` is append-only — corrections are new entries, never edits to old
ones. Every completion claim carries an `EVIDENCE <sha> /Silid/<path>:<line>`
tag, and a tag proves only what it can: that the path was **committed** at that
sha. `git cat-file -e <sha>:<path>` must succeed. So **commit the code first,
then commit the PROGRESS.md entry that cites it** — a tag pointing at a
not-yet-existing commit is not evidence, it is a promise. A spec change lands
in the same commit as its `spec/CHANGELOG.md` entry.

## 6. Scope discipline

Build the phase in `roadmap/`, in order, to its Definition of Done. Do not
re-open a closed phase to re-litigate it. Work that is not the builder's to
close — an operator credential, a dashboard-only value, a runner review gate —
gets recorded and handed over, not silently absorbed or quietly dropped.
